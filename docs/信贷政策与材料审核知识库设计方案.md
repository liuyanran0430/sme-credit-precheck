# 信贷政策与材料审核知识库设计方案

> 版本：v1.0 ｜ 日期：2026-11-07
> 适用项目：小微企业授信智能预审系统（sme-credit-precheck）

---

## 一、知识库目标与定位

### 1.1 建设目标

将分散在代码硬编码、YAML 规则文件、业务文档中的**信贷政策**与**材料审核标准**统一沉淀为结构化知识库，实现：

1. **政策可追溯**：每条准入规则、评分阈值、结论口径均有明确出处与版本，历史报告可回溯到当时生效的政策版本；
2. **审核标准化**：材料完整性、一致性校验、分类判定的规则从代码中解耦，沉淀为可配置、可检索的知识条目；
3. **AI 可解释**：RAG 检索为 LLM 提供规则原文与政策依据，AI 预审结论附带证据溯源，杜绝口径漂移与幻觉；
4. **运营可维护**：业务人员可独立维护知识库内容，无需改代码，版本变更自动触达预审流程。

### 1.2 与现有系统的关系

| 现有组件 | 知识库角色 | 关系 |
|---|---|---|
| `knowledge_base/03_规则配置/准入规则/rule_*.yaml` | 产品准入规则的**机器可执行**载体 | 知识库的「政策条款」是规则的**业务语义来源**，YAML 是其**编译产物** |
| `services/analyzer.py` | 规则执行引擎 | 执行 YAML，不直接读知识库；RAG 仅在需要解释/兜底时检索知识库 |
| `app/rag/` 向量库 | 知识库的**检索入口** | 知识库内容经 Embedding 后入向量库，供 LLM 证据溯源 |
| `materials.ocr_text` | 材料事实数据 | 知识库提供「审核标准」，OCR 提供「事实」，两者比对得出结论 |

**核心原则**：知识库是「业务知识的单一事实来源」，YAML 规则与代码逻辑是知识库的**执行化投影**。变更政策优先改知识库，再同步 YAML。

## 二、知识库总体架构

### 2.1 三层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    L1 业务知识层（自然语言）                    │
│   政策条款原文 · 审核要点说明 · 术语解释 · 异常案例 · 口径说明    │
└───────────────────────┬─────────────────────────────────────┘
                        │ 结构化抽取
┌───────────────────────▼─────────────────────────────────────┐
│                   L2 结构化知识层（YAML/JSON）                  │
│   规则条目 · 评分配置 · 结论口径 · 校验规则 · 分类标准           │
└───────────────────────┬─────────────────────────────────────┘
                        │ 编译/加载
┌───────────────────────▼─────────────────────────────────────┐
│                  L3 执行层（代码 + 向量索引）                    │
│   rule_config 加载 · analyzer 执行 · RAG 向量检索              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 知识库存储形态

知识库采用 **「Markdown 原文 + YAML 结构化条目」双形态**存储：

- **Markdown（.md）**：面向业务人员阅读、编辑、评审，承载政策原文、说明文字、案例；
- **YAML（.yaml）**：面向机器加载，承载规则参数、阈值、判定逻辑，是 L1 内容的结构化投影；
- **向量索引（Chroma）**：由 Markdown/YAML 内容生成 Embedding 后入向量库，供 RAG 检索。

### 3.1 与运行时规则加载的关系

`app/services/rule_config.py` **直接读取** `knowledge_base/03_规则配置/准入规则/` 下的
`rule_<产品>.yaml` 作为运行时规则，不再使用 `sme-credit-precheck-backend/rules/` 目录。

```
知识库规则源 (knowledge_base/03_规则配置/准入规则/)
        │  审核通过（validate_kb.py 校验）
        ▼
运行时规则（rule_config.py 直接加载，无需复制同步）
```

> `sme-credit-precheck-backend/rules/` 已废弃，可整体删除。

## 四、信贷政策知识库设计

### 4.1 政策条款条目结构

每款产品的政策文件（如 `普惠小微经营贷.md`）按以下结构组织：

```markdown
# 普惠小微经营贷（产品代码 AP）

## 一、产品定位
客群、额度区间、期限、担保方式、核心卖点

## 二、准入条件
### 2.1 强规则（硬性门槛，不满足直接拒绝）
| 规则编号 | 规则名称 | 判定条件 | 政策依据 |
|---|---|---|---|
| AP-H01 | 营业执照存续 | 登记状态 ∈ {存续, 在营, 开业} | 《信贷准入管理办法》第3条 |
| AP-H02 | 成立年限 ≥ 2 年 | 成立日期至申请日 ≥ 24 个月 | 同上第5条 |
...

### 2.2 弱规则（影响评分，不直接拒绝）
| 规则编号 | 规则名称 | 判定条件 | 阈值 | 权重 |
|---|---|---|---|---|
| AP-S01 | 流水进账 ≥ 年营收 70% | 12月流水贷方合计 / 年营收 ≥ 0.70 | 0.70 | +14分 |
...

## 三、评分标准
基础分、弱规则得分、等级阈值（A/B/C/D）

## 四、材料要求
必交材料清单 + 产品专属材料要求

## 五、结论口径
强规则FAIL → 拒绝；缺件 → 转人工；一致性高风险 → 关注；≥3条弱规则FAIL → 关注；其余 → 通过
```

### 4.2 评分体系知识

`评分体系.md` 统一说明四款产品共用的评分模型：

| 维度 | 说明 |
|---|---|
| 基础分 | 强规则全部 PASS 即得，AP/AE=2 分，AK/AJ=4 分 |
| 弱规则得分 | 每条弱规则 PASS 加分，AP/AE=14 分/条，AK/AJ=16 分/条 |
| 等级阈值 | A(≥90) / B(75-89) / C(60-74) / D(0-59) |
| 等级处理建议 | A 自动审批 · B 优先审批 · C 人工复核 · D 谨慎受理或降额 |

### 4.3 结论口径知识

`结论口径.md` 定义四类结论的判定优先级（从高到低）：

1. **拒绝（reject）**：任一条强规则 FAIL；
2. **转人工（manual）**：材料缺件或内容不可读；
3. **关注（attention）**：一致性校验 HIGH 级别 FAIL，或 ≥3 条弱规则 FAIL；
4. **通过（pass）**：其余情况，按得分划分 A/B/C/D 等级。

## 五、材料审核知识库设计

### 5.1 材料分类标准

`材料分类标准.md` 定义六类材料的分类边界与识别要点：

| 类别编码 | 中文名称 | 识别特征 | 典型文件 | 易混淆类别 |
|---|---|---|---|---|
| business_license | 营业执照 | 含「营业执照」「统一社会信用代码」 | 营业执照正本/副本 | — |
| bank_statement | 银行流水 | 含「对账单」「交易明细」「借方/贷方」 | 银行对账单 | 财务报表 |
| financial_report | 财务报表 | 含「资产负债表」「利润表」「现金流量表」 | 年度审计报告 | 银行流水 |
| tax_return | 纳税申报表 | 含「纳税申报表」「纳税人识别号」 | 增值税/所得税申报表 | 财务报表 |
| credit_auth | 征信授权书 | 含「征信」「授权」「签署日期」 | 个人/企业征信授权书 | — |
| other | 其他 | 置信度 < 0.6 或无法归入上述五类 | 抵押物证明、科技资质证书 | — |

**分类置信度规则**（与现有代码一致）：
- 置信度 ≥ 0.6：按 AI 分类结果归档；
- 置信度 < 0.6：归入「其他」，转人工分类；
- 分类依据字段 `reason` 记录 AI 判定理由，供人工复核参考。

### 5.2 完整性要求

`完整性要求.md` 定义材料齐全度标准：

**五大公共必交材料**（所有产品均需提供）：
1. 营业执照（≥1 份）
2. 银行流水（≥1 份，需覆盖 >6 个月）
3. 财务报表（≥1 份，需三表齐全：资产负债表、利润表、现金流量表）
4. 纳税申报表（≥1 份）
5. 征信授权书（≥1 份，签署日期需在近 6 个月内）

**产品专属必交材料**（从规则文件 `required_categories` 读取）：
- 经营性抵押贷（AJ）：抵押物证明 ≥1 份（抵押合同/评估报告/房产证/租赁合同）
- 科技e贷（AE）：科技资质证书 ≥1 份（高新技术/专精特新/知识产权证书）

**内容可读性要求**：
- OCR 文本为空 → 视为内容不完整，需重传；
- 银行流水无法识别交易期间 → 转人工核验。

### 5.3 一致性校验规则

`一致性校验规则.md` 定义 P1 核心校验项（与现有 `analyzer.check_consistency` 对应）：

| 校验编号 | 校验项 | 严重度 | 判定逻辑 | 处置建议 |
|---|---|---|---|---|
| C1 | 企业名称一致性 | HIGH | 各来源企业全称归一化后唯一 | 不一致 → 以营业执照为准核实 |
| C2 | 统一社会信用代码一致性 | HIGH | 各来源 18 位代码一致 | 不一致 → 核实原件 |
| C5 | 银行流水期间连续性 | MEDIUM | 交易期间无断月 | 缺失月份 → 补充流水 |
| C6 | 财报与纳税年度一致性 | MEDIUM | 财务报表年度 = 纳税申报所属年度 | 不一致 → 核实报表期间 |
| C7 | 征信授权时效 | HIGH | 签署日期 ≤ 6 个月且未过期 | 过期 → 重新签署 |
| C9 | 材料日期时效 | HIGH | 材料日期 ≤ 申请提交日期+1天 | 晚于 → 核实材料真实性 |
| C14 | 银行流水勾稽平衡 | HIGH | 期初+收入-支出=期末 | 不平 → 核实原始对账单 |
| C15 | 资产负债表恒等式 | HIGH | 资产=负债+所有者权益 | 不平 → 核实报表 |

**三态判定**：pass / fail / uncertain，字段缺失时标记为 uncertain 并提示转人工核验。

### 5.4 各材料审核要点

每类材料单独一份文档，包含：
- **必填字段清单**：该类材料必须抽取哪些字段（如营业执照需抽取：企业名称、统一社会信用代码、法定代表人、成立日期、登记状态、营业期限）；
- **字段抽取规则**：正则表达式或关键字定位方式（如信用代码 18 位、成立日期格式 `YYYY年MM月DD日`）；
- **校验规则**：字段间的勾稽关系（如资产负债表恒等式）；
- **常见问题与处置**：OCR 识别异常、字段缺失、格式不符的处理方式。

以营业执照为例：

```markdown
## 营业执照审核要点

### 必填字段
| 字段名 | 说明 | 抽取方式 |
|---|---|---|
| 企业名称 | 工商注册全称 | 关键字「名称」后匹配 |
| 统一社会信用代码 | 18 位编码 | 正则 `[0-9A-Z]{18}` + GB32100 校验 |
| 法定代表人 | 自然人姓名 | 关键字「法定代表人」后匹配 |
| 成立日期 | YYYY-MM-DD | 关键字「成立日期」后匹配 |
| 登记状态 | 存续/在营/开业等 | 关键字匹配 |
| 营业期限 | 起止日期 | 关键字「营业期限」后匹配 |

### 校验规则
- 信用代码格式：18 位且校验位合法（GB 32100 加权算法）；
- 成立年限：申请日 - 成立日期 ≥ 产品要求月数；
- 登记状态：必须 ∈ {存续, 在营, 开业}，否则拒绝。

### 常见问题
- OCR 将「存续」识别为「存结」→ 兜底按营业期限推断；
- 信用代码识别缺失 → 用申请信息中的 credit_code 兜底。
```

## 六、知识库与 RAG 集成方案

### 6.1 检索场景

根据项目既有约束（RAG 仅作证据溯源、字段抽取兜底、规则解释，不接管判定），知识库 RAG 检索用于以下场景：

| 场景 | 检索内容 | 用途 |
|---|---|---|
| 规则解释 | 政策条款原文 + 规则 detail_zh | AI 预审报告中展示规则的业务依据 |
| 字段抽取兜底 | 该字段的审核要点文档 | OCR 抽取失败时，LLM 参考知识条目辅助抽取 |
| 冲突溯源 | 一致性校验规则 + 各材料审核要点 | 出现数据冲突时，提供判定依据与处置建议 |
| 客户经理咨询 | 产品政策 + FAQ | 前端问答或预审报告中的政策说明 |

### 6.2 向量库 Collection 规划

复用现有 `app/rag/` 抽象层，规划以下 Collection：

| Collection 名 | 内容来源 | 元数据过滤字段 |
|---|---|---|
| `kb_policy` | 01_信贷政策/ 下所有 .md | product, rule_id, kind(hard/soft) |
| `kb_material_review` | 02_材料审核标准/ 下所有 .md | category, check_item |
| `kb_rule_config` | 03_规则配置/ 下所有 .yaml | product, rule_id, version |
| `kb_cases` | 04_案例与FAQ/ 下内容 | case_type, product |

### 6.3 检索过滤策略

严格遵循项目约束：**RAG 检索必须按申请硬过滤，禁止跨申请检索**。知识库检索时：

- 检索政策类内容：按 `product` 过滤，只返回当前申请产品的政策；
- 检索材料审核类：按材料 `category` 过滤，只返回相关类别的审核要点；
- 检索案例类：按 `product` + 异常类型过滤。

### 6.4 降级与容错

- Embedding 不可用 → 自动降级为关键词检索（按 rule_id / category 精确匹配）；
- 检索异常 → 仅输出 WARNING 日志，不中断 AI 预审主流程；
- 检索结果为空 → LLM 直接使用 YAML 规则中的 `detail_zh` 字段，不强制要求知识库命中。

## 七、知识库生命周期管理

### 7.1 版本管理

- 知识库整体版本号：`vYYYY-MM-DD`，与规则文件 `version` 字段一致；
- 每条知识条目带 `created_at` / `updated_at` / `effective_date`；
- `index.yaml` 记录当前版本、条目总数、各分类条目数、最后更新时间。

### 7.2 变更流程

```
业务人员编辑知识库 .md / .yaml
        │
        ▼
  提交 PR / 审核
        │
        ▼
  校验脚本 (scripts/validate_kb.py)
   - YAML 语法校验
   - 规则编号唯一性校验
   - 阈值合理性校验
   - 与现有 applications 产品枚举一致性校验
        │
        ▼
  直接生效（rule_config.py 读取 knowledge_base/03_规则配置/准入规则/）
        │
        ▼
  重建向量索引 (scripts/rebuild_vector_index.py)
   - 读取知识库内容
   - 调用 LLM embed
   - upsert 到对应 collection
```

### 7.3 历史版本回溯

- 每次规则变更生成快照，存入 `ai_reports.rule_snapshot` 字段（已有能力）；
- 历史报告通过 `rule_version` 关联到当时生效的知识库版本；
- 知识库目录可通过 Git 历史回溯任意版本。

## 九、与现有代码的对齐清单

以下是知识库内容与现有代码的对应关系，确保知识库建设时不出现口径不一致：

| 知识库内容 | 现有代码位置 | 对齐要点 |
|---|---|---|
| 产品准入规则 | `knowledge_base/03_规则配置/准入规则/rule_*.yaml` | 规则编号、阈值、操作符完全一致 |
| 材料类别编码 | `schemas/ai_classification.py` | 6 类编码与 CATEGORY_LABELS 一致 |

| 完整性判定 | `services/analyzer.py:analyze_completeness` | 最小份数、流水月数、三表要求 |

| 评分配置 | `knowledge_base/03_规则配置/准入规则/rule_*.yaml:scoring` | 基础分、弱规则分、等级阈值 |
| 结论口径 | `knowledge_base/03_规则配置/准入规则/rule_*.yaml:conclusion_logic` | 四类结论优先级 |

## 十、风险与约束

1. **不修改现有核心判定逻辑**：知识库建设不改变 `analyzer.py` 的规则执行逻辑，仅补充政策依据与解释；
2. **YAML 仍是运行时唯一规则源**：`rule_config.py` 直接读取 `knowledge_base/03_规则配置/准入规则/`，无需同步复制；
3. **RAG 不接管判定**：知识库检索结果仅用于解释与兜底，最终结论仍由 YAML 规则执行得出；
4. **敏感信息脱敏**：知识库中的案例内容遵循现有脱敏规则（信用代码掩码、金额脱敏）。
